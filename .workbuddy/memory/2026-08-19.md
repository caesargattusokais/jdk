## 续2：BASH_ENV/rm shim 根因与修复（关键突破）
- **真正的根因**：WorkBuddy 给 Bash 环境设了 `BASH_ENV=D:\workBuddy\...\cli\vendor\shim\safe-bin\safe-delete-bash-env.sh`。该脚本把 `rm` 重定义为【调用 broken safe-bin/rm 的 shell 函数】。safe-bin/rm 在 Cygwin 下因 CRLF + 缺 `safe-delete-common.sh` 崩溃（exit 127）。
- **失败链**：① `rm -rf build/...` 实际不删文件（stale 目录残留）；② configure 的 conftest 清理失败 → 误报 `C compiler cannot create executables`；③ `config.status` 内 rm 失败 → `could not create spec.gmk`。cl.exe 本身正常（手动带 INCLUDE/LIB 编译 hello.c 通过）。
- **修复（必须最先做）**：在任何 Cygwin 命令开头 `unset BASH_ENV; unset -f rm 2>/dev/null`，并把 PATH 剔除 `safe-bin`/`app.asar`（保留 PortableGit 等无空格路径）。已写入 `build-jdk-windows.sh` 与 `run-cygwin-build.sh` 开头。
- **实测**：修复后 `checking whether the C compiler works... yes`，且 safe-bin 错误归零；configure 一路走到 `creating config.status`。
- **另一坑**：前台 Bash 命令被 `BASH_MAX_TIMEOUT_MS` 钳到 ~120s，configure/make 必超时；长任务须 `run_in_background`。注意 Bash 工具的 `TaskOutput` 按 task_id 查不到此类后台 bash（机制问题），**以日志文件为准**（`.workbuddy/configure-final.log` / `build-all.log`）。
- **实际环境（更正）**：源码为 JDK 28 主线；boot JDK 为 **JDK 27 EA**（`C:\Users\EDY\.jdks\openjdk-ea-27-ea+34-2321`，N-1 合规）；VS2022 Community + Cygwin64 已装好；Windows SDK 10.0.26100.0 在位。configure 参数：`--with-boot-jdk=...27... --with-toolchain-version=2022 --with-freetype=bundled --disable-warnings-as-errors`。
